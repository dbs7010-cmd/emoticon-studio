# vc4 — 로그인 · PRO 클라우드 백업 · 자체 공모전: 측정 · 비용 · 설계 (2026-10-07)

> 상태: **설계·로컬 구현 단계.** 운영자 계정(Firebase·카카오·네이버·구글)·결제 등록 전. 아래 비용은 공식 가격 페이지를 2026-10-07 에 확인한 값이며 계산 근거를 함께 적는다.

## 1. 실제 용량 (측정)
측정 방법: 에뮬레이터 '몽이의 하루' 실제 작품 파일 + 앱 엔진 그대로(Edge, `scripts/promo/set-size-measure.cjs`, 12fps = 앱 baker 와 같음). 결과 `verification/vc4/set-sizes-promo.json`.

| 묶음 | 구성(내보내기 규칙 그대로) | 측정 |
|---|---|---|
| 정지 세트 제출 묶음 | PNG 32 + 아이콘·공유 | **0.63 MB** (PNG 평균 18.7 KB, 최대 21.7 KB) |
| 움직임 세트 제출 묶음 | WebP 24 + 공식 도구용 프레임 PNG 321장 + 아이콘·공유 | **11.5 MB** (WebP 평균 115.9 KB·최대 217 KB, 프레임 평균 27.8 KB) |
| 〃 프레임 폴더 제외 | WebP 24 + 아이콘·공유 | 2.76 MB |
| 편집 원본(백업용) 정지 칸 | 레이어 PNG + 완성 PNG + 세트 정보 | 칸당 **36.2 KB** → 32칸 약 1.2 MB |
| 편집 원본 움직임 칸 | + GIF + WebP | 칸당 **195.1 KB** → 24칸 약 4.7 MB |

한계: 측정 그림은 **선 그림(색 적음)**이다. 색칠·질감이 많은 그림은 PNG·WebP 가 커진다 — 비용은 측정값과 '무거운 그림(×4)' 두 가지로 냈다. 카카오 규격 상한(정지 PNG 150 KB, 움직임 WebP 650 KB)까지 가면 정지 묶음 약 4.9 MB, 움직임 WebP 만 15.6 MB(+프레임)다.

**용량 제한 제안(측정 근거, 세트 구성은 줄이지 않음):** 공모전 제출 1건 최대 **120 MB**(카카오 상한 WebP 15.6 MB + 프레임 321장 × 150 KB ≈ 63 MB 의 약 2배 여유), PRO 개인 백업 1인 **1 GB**(움직임 세트 무거운 그림 ≈ 19 MB × 50세트). 넘으면 거절이 아니라 이유를 알리고 운영자에게 문의하게 한다.

## 3. 서버 구성 (Firebase, 계정 없이 로컬 에뮬레이터로 먼저 검증)
| 부분 | Firebase 서비스 | 하는 일 |
|---|---|---|
| 로그인 | Authentication + Functions | 구글: Firebase 구글 로그인. **카카오·네이버: 앱이 받은 액세스 토큰을 Functions 가 각 회사 서버(카카오 `GET kapi.kakao.com/v1/user/access_token_info` 의 `app_id` 를 우리 앱 ID 와 대조 — 공식 문서 확인·`/v2/user/me`, 네이버 `openapi.naver.com/v1/nid/me` — **네이버 공식 문서는 이 환경에서 열리지 않아 직접 대조 못 함, 계정 개설 때 확인**)에 직접 확인**하고 Firebase 커스텀 토큰을 발급. 앱이 보낸 사용자 번호를 믿지 않는다 |
| 회원 DB | Firestore `users/{uid}` | 제공자·가입일·PRO 상태(서버만 씀)·백업 사용량 |
| PRO 권한 | Functions + Firestore | `users/{uid}.entitlement` 는 **서버만** 쓴다(규칙으로 앱 쓰기 금지). 지금은 구매 검증 미구현 → 체험(test) 과 실제 구매를 다른 값으로 둔다 |
| 개인 백업 | Storage `backups/{uid}/blobs/{sha256}` + Firestore `backups/{uid}/sets/{setId}` | 파일은 **내용 해시 이름**으로 한 번만 저장(바뀐 칸만 전송). 규칙: 본인 + PRO(서버가 쓴 값)만 읽기·쓰기 |
| 공모전 접수 | Storage `contests/{contestId}/{uid}/{submissionId}/package.zip` + Firestore `contests/{id}/submissions/{submissionId}` | 앱이 만든 **세트 전체 묶음**(내보내기 ZIP 그대로)을 제출 당시 사본으로 보관. 접수번호 = 앱이 만든 제출 키(재시도해도 같은 번호 → 중복 접수 없음). 서버 함수가 ZIP 을 열어 칸 수·형식·크기 확인 후 '접수됨' |
| 관리자 | Hosting 정적 페이지 + Functions(관리자 권한 claim) | 공모전 등록, 접수 목록·전체 세트 미리보기·ZIP 다운로드(서명된 단기 URL), 심사 상태, 결과 발표. **관리자 비밀키는 앱·저장소에 없다** — 관리자는 구글 로그인 + 서버가 준 `admin` 권한으로만 |

출품: 카카오 이모티콘 스튜디오는 **창작자 본인 계정으로 직접 제안**하는 구조이고 공개된 자동 제출 API 를 확인하지 못했다(→ 자동 출품을 약속하지 않음). 선정작은 관리자 페이지에서 '출품 묶음'(기존 내보내기 규칙: 정지 PNG 32 + 아이콘 / 움직임 WebP 24 + 공식 도구용 프레임 + 읽어주세요)을 내려받고, 제출 주체(작가 본인 또는 운영자-작가 계약)와 절차를 문서로 안내한다.

## 4. 앱 흐름
- 로그인 없이: 지금 기능 전부(그리기·기기 저장·파일 백업·공유).
- 로그인(카카오·네이버·구글) → 설정에 계정 · 로그아웃 · **탈퇴(서버 데이터 삭제 요청)**.
- PRO 클라우드 백업: PRO 만. 세트별 '클라우드에 백업' · 진행/실패/마지막 백업 시각 · 재설치 후 같은 계정 → 목록 → **기존 기기 작품과 겹치면 사본으로 들임(덮어쓰기 없음)**. PRO 가 끝나면 서버 작품은 즉시 지우지 않는다 — 보관·다운로드 정책은 운영자 결정(제안: 읽기 전용 90일 + 전체 백업 파일 내려받기 가능 → 이후 삭제 예고 후 삭제).
- 공모전: 공지·참가 조건 → 로그인 → 세트 선택(규격 점검 재사용) → 제출 확인·동의(권리·이용 범위) → 전체 업로드(진행률·실패 시 이어 올리기) → 접수번호·상태(접수됨/검토 중/선정/비선정).
- **서버 주소·키가 없는 빌드에서는 '준비 중'으로만 보이고, 제출·백업이 된 것처럼 표시하지 않는다.**
