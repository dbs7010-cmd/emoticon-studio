# 45.13 — 저장 번호의 보호 범위 · 저장 잠금의 실제 모습 · 실기기 검수 준비 (2026-09-21)

자동 검사는 실제 앱 코드를 불러 돌린다(`scripts/ux-test.cjs`, `scripts/fill-test.cjs`). 실기기·에뮬레이터는 이번에도 없다(E 절).
45.10~45.12 수정(기본 1장 · 장 id 충돌 방지 · 문구 색 입구 · 연필 · 문구 외곽선 맞춤 · 도톰 굵기 · 저장 번호)은 그대로 두고, 도톰·연필 수치는 건드리지 않았다.

## A. 저장 요청 번호(token)가 어디까지 지키나 — 파일 쓰기 경쟁은 **일어날 수 없는 구조**였다

질문한 순서(A 응답 → A 쓰기 지연 → B 요청·응답 → B 쓰기 → A 쓰기)는 **중간에 기다림(await)이 있어야** 만들어진다.
지금 경로에는 그 기다림이 없다. 확인한 곳:

| 단계 | 코드 | 성질 |
|---|---|---|
| 캔버스 응답 받기 | `src/painter/painter.tsx:709` `onMessage={event => {` | **동기 함수**(async 아님, 안에 await 없음) |
| 그림 파일 쓰기 | `src/services/images.ts:79` `savePainterWork` → `saveDrawing`(34) | `file.write` + `bytesSync()` 검증까지 **동기** |
| 움직이는 파일 | `images.ts:57,67` `saveMotionLoop`·`saveSubmitLoop` | 동기(쓰고 바로 헤더 확인) |
| 세트 저장 | `src/services/storage.ts:89` `saveStore` | `file.write` 뒤 `textSync()` 로 되읽어 검증, **동기** |
| 두 번째 요청 막기 | `painter.tsx:440` `if (inFlight.current) { … queued … return; }` | 진행 중이면 새 요청을 보내지 않고 **미뤄 둔다** |
| 캔버스 쪽 차례 | `src/painter/canvas-html.ts:914` `pending=pending.then(()=>command(m))` | 명령이 **한 줄로 차례차례** 처리된다 |
| 칸 이동 | `App.tsx:1273` `<Painter key={project.id + '/' + slot.number}>` | 칸이 바뀌면 그리기 화면과 WebView 가 **새로 만들어진다** — 옛 화면의 응답이 남아 다른 칸에 닿지 않는다 |

**동작으로 못 박았다**(`ux-test`, 45.13 회귀): 저장 응답을 넣은 **그 호출이 돌아오기 전에** 저장 파일이 이미 쓰여 있고 캔버스에도 완료를 알린 상태다.
이 검사는 응답 처리 중간에 `await` 를 하나만 넣어도 실패한다(그 상태로 되돌려 실패를 확인했다).

그래서 질문한 네 가지는 지금 구조에서 다음과 같다.
- **최종 파일에 최신 내용이 남는가** — 한 번에 하나씩만 쓰므로 마지막에 받아들인 응답이 그대로 남는다.
- **이전 완료가 최신 요청의 상태·dirty·잠금을 바꾸는가** — 번호가 다른 응답은 파일도 쓰지 않고 `saved` 로 답하지도 않는다(45.12 회귀). 캔버스도 번호가 다른 `saved`/`saveFailed` 를 무시한다.
- **칸 이동·재진입 뒤 옛 응답이 다른 칸에 적용되는가** — 그리기 화면이 칸마다 새로 만들어져 옛 WebView 의 응답 자체가 오지 않는다. 그 위에 번호 검사가 한 겹 더 있다.
- **재시도마다 쓰기가 중복되는가** — 받아들이는 응답이 번호당 하나뿐이라 한 번만 쓴다(응답이 늦어 접은 요청은 나중에 와도 버린다).

**말을 좁혀 둔다**: 이번에 확인한 것은 "지금 코드에는 파일 쓰기 사이에 끼어들 틈이 없다" 이고, 저장 경로를 비동기로 바꾸면 이 보장은 사라진다. 번호 검사만으로 경쟁이 해결된다는 뜻이 아니다.
`expo-file-system` 의 동기 API 가 실제 기기에서도 동기로 동작하는지는 **기기 검수 항목**으로 남긴다(E 절).

## B. 저장 잠금 — 사용자가 실제로 보는 것과 할 수 있는 것

"엔진이 재시도를 받는다"(45.12)와 "사람이 앱에서 다시 저장할 수 있다"는 다른 말이다. 화면 쪽을 따로 확인했다.

| 상황 | 화면에 보이는 것 | 할 수 있는 것 |
|---|---|---|
| **보통 저장**(응답이 곧 온다) | 머리 오른쪽 작은 구름(`저장 중`) → 체크(`저장됨`) 1.2초. 캔버스에는 아무 말도 없다 | 저장은 한 번의 왕복 안에 끝난다. 칸을 떠나는 저장(닫기·완성·이동·공유) 동안만 닫기·완성·도구 줄이 잠깐 잠긴다(자동저장은 잠그지 않는다) |
| **응답이 늦거나 사라짐** | **1.5초가 지나면** 캔버스 위에 `저장 중이에요 · 잠시만요`(읽어 주는 이름: `저장 중이라 잠시 그릴 수 없어요`) — 45.13 추가 | 기다린다. 그동안 그은 획은 캔버스에 닿지 않는다(스냅숏 보호) |
| **20초까지 응답 없음** | 알림창 `저장이 늦어지고 있어요` — 본문을 고쳐 **무엇을 누르면 다시 저장되는지** 적었다(45.13) | 잠금이 풀려 **바로 다시 그릴 수 있다**. 다시 저장은 자동저장(40초 주기·앱을 내릴 때)·닫기·완성 중 아무거나 |
| **저장 실패**(파일 쓰기 오류) | 알림창 `저장하지 못했어요` + 이유 | 그림은 화면에 그대로, `dirty` 도 그대로. 기존 저장본은 건드리지 않는다. 세트 파일 쓰기가 실패하면 홈·보드 위에 `다시 저장` 버튼 배너(`App.tsx:523`) |

- **"최대 20초"는 정상 저장 시간이 아니다.** 응답이 오지 않을 때 화면이 포기하는 한계값이다. 보통 저장은 응답 한 번으로 끝난다(A 절의 회귀가 그 사실을 고정한다).
- 그리기 화면에는 저장 버튼이 없다(작업은 스스로 저장된다). 그래서 재시도 경로가 무엇인지 알림창이 직접 말하도록 바꿨다.
- 45.13 회귀(`ux-test`): 보통 저장에서는 캔버스가 아무 말도 하지 않는다 / 길어지면 이유를 적는다 / 시간초과 뒤에는 알림이 걷히고 `saveFailed` 를 **그 번호로** 보내며 다시 저장을 부를 수 있고 정상으로 끝난다. 알림·문구를 되돌리면 각각 실패한다(확인했다).
- 바꾸지 않은 것: 저장 중 입력 잠금 자체, 20초라는 시간, 자동저장 주기. 입력을 열려면 '스냅숏 이후의 편집'을 따로 세어야 해 저장 구조가 바뀐다(45.12 B 절과 같은 판단).

## C. 이번에 고치지 않은 관찰
- **검사 하네스의 타이머 누수**: `ux-test` 는 App 트리를 여러 번 만들면서 일부를 `unmount` 하지 않는다. 그래서 옛 트리의 타이머가 목록에 남는다. 앱 코드의 누수가 아니다(화면이 살아 있는 동안에는 저장마다 하나뿐이고, 끝나면 지운다). 검사 편의 문제라 그대로 뒀다.
