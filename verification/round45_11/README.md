# 45.11 — 레이어 id 충돌 · 미리보기와 내보낸 PNG 차이의 실제 원인 (2026-09-21)

실행 환경: Windows 11 Pro x64 · Node 24 · 앱이 WebView 에 넣는 **실제 캔버스 엔진**(`engine.html`, 45.11 상태에서 추출)을
localhost:4603 으로 띄워 브라우저에서 렌더. 글꼴은 이 PC 의 것 → **Android 글꼴 검증 아님**. 앱 화면(RN) 캡처는 이번에도 BLOCKED(D 절).
자동 검사는 실제 앱 코드를 불러 돌린다(`scripts/fill-test.cjs`, `scripts/ux-test.cjs`).

## A. 레이어 id 충돌 — 재현됨 → 고침

### 재현 (고치기 전, `layer-id-before-fix.txt`)
장 id 를 `draw-(장 수 + 1)` 로 지었다. draw-1·draw-2·draw-3 을 만들고 **가운데 draw-2 를 지운 뒤 한 장 추가**하면:

| 확인한 것 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 장 목록 | `draw-1, draw-3, draw-3` (**같은 id 둘**) | `draw-1, draw-3, draw-2` |
| 새 획이 닿는 곳 | 먼저 그린 draw-3 위 (그 장의 픽셀 1,658 → 3,316) | 새 빈 장 (옛 draw-3 은 1,658 그대로) |
| 새 장 선택 | 옛 draw-3 이 선택됨 | 새 장이 선택되고 비어 있음 |
| 'draw-3 숨기기' | 앞쪽 draw-3 이 숨겨짐(목록에서 누른 것과 다를 수 있음) | 누른 장만 숨겨짐 |
| 'draw-3 지우기' | 같은 id 의 다른 장이 남는데도 **부분 움직임이 함께 사라짐** | 대상이 사라질 때만 함께 정리 |
| 화면 목록 | React `key` 가 겹침(같은 이름 '레이어 3' 둘) | 이름·접근성 이름 모두 갈림 |

즉 **그림 유실로 보이는 상황(옛 그림 위에 덧그리기)과 부분 움직임 유실**까지 이어지는 실제 결함이었다. 45.10 에 P2 로 적어 둔 위험이 재현됐다.

### 고친 방식 (최소)
- `src/painter/canvas-html.ts`: `nextLayerId()` — **지금 장들이 쓰지 않는 가장 작은 번호**를 고른다. 형식은 예전 그대로 `draw-N` 이라 저장 형식·`startsWith('draw-')` 규칙·옛 저장본과 어긋나지 않는다.
  - 쓰는 곳: 장 복제 · 그림 불러오기 · 선택 영역을 새 장으로 · `addLayer`(화면이 보낸 id 가 이미 있으면 엔진이 바꾼다 — 마지막 방어선).
- `src/painter/painter.tsx`: '레이어 추가'도 같은 규칙으로 번호를 고른다.
- 프로젝트에 공용 id 유틸은 없다(참고 이미지는 파일 경로, 부분 움직임은 시각 기반). 그래서 새 유틸을 만들지 않고 장 목록만 보는 함수 하나로 끝냈다.
- 기존 저장본의 id 를 **다시 매기지 않는다.** 이름은 새로 만든 번호를 따르므로 목록에 '레이어 1 · 레이어 3 · 레이어 2' 처럼 번호가 건너뛸 수 있다(이름은 바꿀 수 있고, 각 줄의 이름은 서로 다르다).

### 검증 (`scripts/fill-test.cjs`, 회귀로 고정)
- 가운데 장 삭제 → 추가 / 마지막 장 삭제 → 추가 / 삭제→추가 3회 되풀이 / 저장 → 다시 열기 → 삭제 → 추가 / 복제 — **모두 id 겹침 없음**.
- 같은 검사에서 **먼저 그린 그림의 픽셀 수가 그대로**이고(1,658), 새 장은 비어 있으며, 지우지 않은 장을 가리키는 **부분 움직임 `layerId` 가 유지**된다.
- 화면 쪽(`scripts/ux-test.cjs`): 장이 `draw-1 · draw-3` 인 상태에서 '레이어 추가'를 누르면 `draw-2` 를 보낸다.
- 두 회귀 모두 **옛 코드로 되돌리면 실패**하는 것을 확인했다(각각 `겹치는 id 를 받아도…`, `비어 있는 번호를 쓴다…`).

### 이미 id 가 겹친 저장본 (자동 복구 안 함, `duplicate-save-open.txt`)
- 열면 **세 장 모두 그대로 열린다**(그림 파일은 장마다 다른 파일이라 겹쳐 쓰이지 않았다). 새로 만드는 장은 겹치지 않는 번호를 받는다.
- 남는 문제: 그 두 장은 **고르기·숨기기·지우기가 앞의 것에 걸린다**. 이름을 바꿔도 id 는 그대로다.
- 복구안(넣지 않음, 사용자 판단 필요): ① 열 때 뒤쪽 중복 장에만 빈 번호를 새로 주고 그 장을 가리키는 부분 움직임도 같이 옮긴다 — 데이터를 고쳐 쓰는 일이라 근거 없이 넣지 않았다. ② 아무것도 하지 않고, 사용자가 그 장을 지웠다 다시 만들면 자연히 풀린다.
- 실제로 이런 저장본이 있는지는 **모른다**(앱 저장 폴더를 볼 수 있는 기기가 없다).

## B. '또박 0.7% 차이' — 45.10 설명은 틀렸다

45.10 은 이 차이를 **"PNG 인코딩 경계값"** 이라고 적었다. PNG 는 무손실이므로 그 설명은 근거가 없었다. 이번에 네 가지를 갈라서 다시 쟀다.

1. **PNG 자체가 값을 바꾸는가** — 같은 캔버스의 픽셀과 그 캔버스가 만든 PNG 를 node 에서 직접(캔버스를 거치지 않고) 풀어 비교: **달라진 픽셀 0 / 최대 차이 0** (`preview-vs-export.json` 의 `Z-lossless`, 반투명 계단까지 포함). → **PNG 는 원인이 아니다.**
2. **디코딩한 RGBA 비교** — 화면 캔버스 픽셀 vs 내보낸 PNG(직접 디코딩), 12개 문구×글씨체:
   - 11건은 최대 차이 **1**(도톰은 획이 겹치는 자리에서 **3**), 달라진 픽셀 700~2,300, **글자 픽셀 수는 같거나 최대 4개(0.15%) 차이**. 차이 난 픽셀은 대부분 **양쪽 다 완전 불투명**이라, 투명도 계산이 아니라 **칠하기 반올림** 쪽이다.
   - 1건(`num/serif`, '2026년 1월 1일' 또박)만 최대 차이 **255**, 글자 픽셀 2,646 vs 2,623(**0.87%**) — 45.10 의 '0.7%' 와 같은 정체다.
3. **브라우저에서 PNG 를 다시 그려 재는 방법**(45.10 이 쓴 방법)은 여기에 ±1 을 더 얹는다 — 측정 방법 자체가 잡음을 만든다. 그래서 이번에는 쓰지 않았다.
4. **면적 임계값** 하나로만 보지 않고, 경계 상자·픽셀 단위 비교·눈으로 보기를 함께 썼다.

### 실제 원인
같은 글꼴 문자열을 **화면 캔버스와 내보내는 캔버스가 다르게 잰다**. 그 순간 재 본 값:

| 글꼴 | 앱 화면 캔버스 | 새로 만든 캔버스(내보내기와 같은 종류) |
|---|---|---|
| `700 39px serif` | 261.49 | 261.49 |
| **`700 40px serif`** | **273.00** | **268.20** |
| `700 41px serif` | 274.90 | 274.90 |

- 같은 페이지 안에서 **다른 캔버스 네 종류**(따로 만든 것 · 같은 부모에 넣은 것 · 같은 CSS 를 준 것 · body 에 붙인 것)는 모두 268.20 이었다. **앱이 계속 쓰는 화면 캔버스 하나만** 40px 에서 다르다.
- 재기만 다른 것이 아니라 **그리는 것도 다르다**: 같은 글자를 40px 로 직접 그려 보면 화면 캔버스 269px, 새 캔버스 263px(글자 픽셀 수는 3,692 vs 3,690 으로 거의 같다) — 글자 모양은 같고 **글자 사이 간격만 다르다**.
- 즉 브라우저가 그 캔버스·그 크기에 대해 잡아 둔 글꼴 처리가 달라서 생긴 차이다(가속 경로/글꼴 캐시). **우리 저장·내보내기 경로의 결함이 아니다.** 늘 나는 것도 아니어서(같은 문구가 어떤 판에서는 같고 어떤 판에서는 다르다) 45.10 의 한 번 측정이 '또박만'으로 보인 것이다.

### 영향과 판단
- 글자·색·자리·크기 단계는 같고 **가로로 최대 약 1.8%(270px 중 6px)** 차이다. 눈으로는 구분되지 않는다. 내보낸 파일 자체는 온전하다(A~C 어느 검사에서도 깨진 글자·빈 글자 없음).
- 칸 맞춤이 이 차이로 뒤집힐 수 있는지: 가장 넓은 문구의 실제 폭 318px, 여기에 1.8% 를 더해도 324px 로 328px 안이다. **이번 측정 범위에서는 뒤집히지 않는다.**
- 그래서 **렌더 경로는 고치지 않았다.** 완전히 없애려면 문구를 한 번만 그려 두 경로가 같은 그림을 쓰게 해야 하는데(캐시·무효화 필요) 이번 범위의 '최소 수정' 이 아니다. P3 로 남긴다.

## C. 잘림·속 막힘 — 수치가 아니라 실제 렌더로 확인

45.10 은 "글자 폭 최대 309 < 칸 328 → 잘림 없음" 이라고 적었다. **재 보니 그 수치로는 부족했다.**

- 내보낸 PNG 에서 **흰 테두리까지 포함한 실제 자리**를 쟀더니(`export-boxes.txt`) 긴 문구(또박)가 **가로 332px, 좌우 여백 14px** 로 **16px 여백 규칙을 넘었다**. 칸(360) 밖으로 잘리지는 않았지만 규칙 위반이다.
- 원인: 칸 맞춤이 **글자 획만** 재고 흰 테두리(글자 크기의 22%, 절반씩 양쪽)를 빼먹었다.
- 고침(최소): `captionSpot` 이 **테두리까지 더한 폭**으로 크기를 고른다. 결과 — 긴 문구(또박) 332px/여백 14 → **316px/여백 22**. 다른 문구는 그대로다. 회귀 추가(`fill-test`: 글자+테두리 ≤ 328), 옛 코드로 되돌리면 336 > 328 로 실패한다.
- 저장 형식은 그대로다. 이미 내보낸 파일도 그대로다(다음에 그릴 때부터 한 단계 작게 앉는 문구가 생길 수 있다 — 여백을 넘던 긴 문구에 한해서).

### 눈으로 본 판정(수치와 따로)
- `caption-sheet.png`(12종을 흰 바탕에 얹음), `small-text-zoom.png`(긴 문구 3배), `small-text-8x.png`(8배).
- 기본·또박: 작은 크기에서도 글자 속이 열려 있고 읽힌다. 또박은 이 PC 에서 실제로 다른 글꼴로 그려진다.
- **도톰 + 가장 작은 크기(긴 문구)는 글자 속이 막힌다.** 8배로 보면 '늘 · 루' 같은 가로획이 뭉쳐 한 덩어리가 된다. 큰 크기(안녕하세요·2026년…)에서는 문제없다. → **이번에 고치지 않은 새 발견**(E 절).

## D. BLOCKED (그대로)
- 기기: `adb devices` 결과 **연결된 기기 없음**. 45.10 과 같은 주소로 다시 연결을 시도하지 않았다(같은 실패를 되풀이하지 않는다).
- 에뮬레이터: 기존 AVD 는 arm64(x86_64 호스트에서 불가), x86_64 는 WHPX/AEHD 미활성 — **관리자 권한·재부팅**이 필요해 이번에도 실행하지 않았다.
- 따라서 **앱 화면·키보드·3칸 연속 제작·앱이 저장/내보낸 실제 파일·Android 글꼴**은 UNVERIFIED.

## E. 이번에 고치지 않은 발견 (영향·우선순위만)
1. **도톰이 작은 크기에서 뭉친다(P2)** — 덧대는 획이 글자 크기의 7.5% 라, 18px 쯤에서는 획 사이 틈(약 2px)을 메운다. 영향: 긴 문구를 도톰으로 쓴 칸의 가독성. 최소 수정안: 작은 크기에서만 덧대는 양을 줄인다(예: 24px 미만은 4%). 45.9 에서 사람이 확인한 굵기 비율(1.70×)이 바뀌므로 다시 재고 눈으로 확인해야 한다 — 이번 범위 밖이라 손대지 않았다.
2. **화면 캔버스와 내보내기 캔버스의 글자 간격 차이(P3)** — B 절. 브라우저 쪽 특성이고 눈으로 구분되지 않는다.
3. **저장이 끝났다는 응답(`saved`)이 없으면 엔진이 멈춰 있다(P3, 기존 동작)** — 검증 스크립트를 짜다가 부딪혔다. 앱은 항상 응답을 보내므로 실사용 문제는 아니지만, 저장 실패 경로가 응답을 놓치면 캔버스가 굳는다. 확인만 해 둔다.
